# Downloading models

Downloading a multi-gigabyte file to a phone is a different problem from
downloading a normal file. It will be interrupted — the user switches networks,
the screen locks, the process is killed, the train enters a tunnel — so
resumption is not an optimisation, it is the feature. And a resume that silently
restarts from zero is worse than no resume at all, because the user watches the
progress bar go backwards and cannot tell why.

!!! note "Status"
    Implemented in `:core-download`: `HuggingFaceApi`, `CustomUrlSource`,
    `ModelTransfer` (resolution, ranges, resumption, integrity),
    `ShardedModelResolver`, `ModelStorage`, `StorageQuotaManager`,
    `CompatibilityChecker`, `ModelGarbageCollector`, `DownloadRepository` and
    `ModelDownloadWorker`, with unit tests against MockWebServer covering every
    trap on this page — including a regression test that fails if the redirect's
    ETag is ever used as an `If-Range` validator again.

    Not verified on a device: no download has run on real hardware, over a real
    CDN, or against the Android 15 foreground-service timeout.

## Resolving a Hugging Face file

The download URL is:

```
https://huggingface.co/<org>/<repo>/resolve/<revision>/<path>
```

`<revision>` should be a **commit SHA**, not `main`. A branch pointer means the
bytes behind the URL can change between when the catalogue recorded a hash and
when a user downloads, and the resulting hash mismatch looks like corruption.
[The catalogue](catalog.md) pins revisions for this reason.

This URL **redirects**. `huggingface.co` issues a 302 to a CDN host, and the
bytes come from there. The redirect is not incidental — the distinction between
the two responses is where the most damaging bug on this page lives.

To get a file's size and hash without downloading it, use the tree API:

```
GET https://huggingface.co/api/models/<org>/<repo>/tree/<sha>?recursive=1
```

LFS-backed entries carry an `lfs` object with `size` and `oid`, where `oid` is
the **SHA-256** of the content. That is the integrity reference.

Gated repositories require an `Authorization: Bearer <hf_token>` header and
return 401 or 403 without one. The failure should say "this model requires you to
accept its licence on Hugging Face", not "download failed".

## Range requests and resumption

Hugging Face's CDN supports byte ranges. Resumption is:

```
GET https://cdn…/…                     HTTP/1.1
Range: bytes=1073741824-
If-Range: "<validator>"
```

A correct partial response is **206 Partial Content** with a `Content-Range`
header. A **200 OK** means the server has decided to send the whole file from
byte zero — either because it ignored the range, or because `If-Range` did not
match.

The client must therefore:

* **Check the status code, not just the bytes.** On 206, append to the existing
  partial file. On 200, the partial file is invalid and must be truncated before
  writing — appending a full body to an existing partial produces a file that is
  too large and fails its hash check with no indication of why.
* **Verify `Content-Range` matches the requested offset.** A 206 for a different
  range than you asked for is possible through a misbehaving proxy.
* **Persist the offset from the file on disk**, not from a counter in memory. The
  process will be killed; the file length is the only durable truth.
* **Write to a `.part` file** and rename to the final name only after the hash
  verifies. A partially-written file with the real name will be treated as a
  usable model on next launch.

Run the download in a WorkManager worker with a `Constraints` set the user
controls (unmetered-only by default — a 4 GB download over cellular is a real
bill) and a foreground notification, so the OS gives it the latitude to keep
running.

## The ETag trap

!!! danger "The redirect's ETag is not the CDN's ETag"
    `https://huggingface.co/.../resolve/...` returns a redirect whose headers
    include an `ETag` — and it is the **LFS object's SHA-256**, or a weak
    variant of it. The CDN response that actually carries the bytes has a
    **completely different `ETag`**, generated by the object store and typically
    an MD5-derived, multipart-style tag.

    If you capture the ETag from the first response — the natural thing to do,
    since that is the URL you requested — and later send it as `If-Range`, it
    will never match the CDN's validator. The CDN treats a non-matching
    `If-Range` exactly as the specification requires: it **ignores the Range
    header and returns 200 with the entire file**.

    So every resume silently restarts from byte zero. There is no error, no
    warning, and no log line. On a fast connection during testing you may not
    even notice. On a user's phone, a 4 GB download that is interrupted three
    times transfers 16 GB and looks like the progress bar is broken.

The fix is to be precise about which response you take the validator from:

1. Follow the redirect and note the **final** URL and the **final** response's
   `ETag` and `Last-Modified`. In OkHttp, `response.request.url` after automatic
   redirect following gives you the URL the bytes came from, and
   `response.priorResponse` lets you inspect the redirect separately if you need
   the LFS hash from it.
2. Store that final validator alongside the `.part` file, keyed to the final URL.
3. On resume, send `If-Range` with **that** value, against **that** URL.

Two refinements worth having:

* **CDN URLs expire.** They are signed with a time limit. A resume days later
  will get a 403 from the stale URL, at which point you must re-resolve from
  `huggingface.co` and obtain a fresh signed URL — and then re-validate, because
  the new response's validator should still match if the object is unchanged.
* **Consider omitting `If-Range` entirely** and sending a bare `Range`. You lose
  the atomicity guarantee that `If-Range` provides, but you were not really
  getting it anyway with a mismatched validator, and the final SHA-256 check
  catches any corruption. A bare `Range` at least produces a 206 and an actual
  resume. If you do this, treat any 200 response to a ranged request as "start
  over" and say so in the progress UI.
* **Whatever you do, always verify the SHA-256 at the end.** The validator
  dance is an optimisation to avoid re-downloading; the hash is the correctness
  guarantee. Never skip it because the resume "looked fine".

## Sharded GGUF

Large models are split into parts named:

```
model-00001-of-00003.gguf
model-00002-of-00003.gguf
model-00003-of-00003.gguf
```

Points to get right:

* **All shards are required.** A catalogue entry for a sharded model lists every
  part with its own size and its own SHA-256, and the download is not complete
  until all of them verify. Two of three shards is not a partially usable model,
  it is an unusable one.
* **The naming pattern is load-bearing.** llama.cpp locates siblings by the
  `-%05d-of-%05d` suffix, so the files must keep their original names, sit in the
  same directory, and be numbered from 1. Renaming the first shard to something
  friendlier breaks loading with an error that does not mention naming.
* **Point the loader at the first shard**, or use the explicit split-loading
  entry point; either way, do not attempt to concatenate them. They are not
  fragments of one file, they are separate GGUF containers with their own
  headers.
* **Report progress across the whole set**, not per shard. A progress bar that
  reaches 100% three times is a bug report.
* **Estimate memory from the total** of all shards. See
  [memory](../local-inference/memory.md).

At the small end of the size range that fits on a phone, sharding is uncommon —
most 1–8B GGUF builds are a single file. Handle it anyway; the failure mode when
you do not is a download that appears to succeed and a model that will not load.

## Integrity

The SHA-256 from the LFS metadata is the check. Compute it incrementally while
writing bytes so a 4 GB file is not read twice, keep the running digest state
alongside the `.part` file so it survives a resume, and compare at the end.

On mismatch: delete the `.part` file, do not rename, and tell the user the
download was corrupted and will restart. Do not offer to use it anyway. A GGUF
with a flipped bit may load and produce subtly wrong output rather than failing,
which is far worse than a failed download.

Also verify the GGUF magic (`GGUF` at offset 0) and version before accepting the
file. It is nearly free and catches the case where the CDN returned an HTML error
page with a 200 status, which does happen.

## What is deliberately absent

There is no download of models by the native layer. `LLAMA_CURL` was removed
upstream and is
[never passed to CMake](../local-inference/native-build.md); everything on this
page is Kotlin in `:core-download`. Keeping network access out of the native
layer means one place to enforce metered-network policy, one place to handle
credentials, and no libcurl in the APK.
